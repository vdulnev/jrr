# JRiver Remote 2.4.8

## Highlights

- **Official macOS and iOS / iPadOS builds.** Tagged releases now publish
  `JRiverRemote-macOS.zip` (ad-hoc signed) and `JRiverRemote-iOS.ipa`
  (unsigned) on the GitHub Releases page, alongside the existing Android,
  Windows, and Linux artifacts.
- **iOS Local Network permission.** Adds the
  `NSLocalNetworkUsageDescription` Apple requires for any app on iOS 14+
  to talk to a server on the local network — without it the app would
  appear to launch but silently fail to reach Media Center.
- **Build-from-source guide.** A complete walkthrough in the README for
  installing prebuilt unsigned binaries (sideloading paths included) and
  for building from source with Xcode end-to-end.
- **Refactored player core.** Local and remote (MCWS) playback now share
  a single `PlayerController` interface, so every player command is one
  line in the unified provider instead of an `if (zone.isLocal) ... else
  ...` block. Lays the groundwork for adding new transports.

## What's new

### Distribution

- New `build-macos` job in the release workflow archives a universal
  `.app` bundle, ad-hoc signs it with `codesign -s -`, verifies the
  signature with `codesign --verify --deep --strict`, and uploads
  `JRiverRemote-macOS.zip`.
- New `build-ios` job builds the IPA with `--no-codesign` and uploads
  `JRiverRemote-iOS.ipa` for sideloading.
- Pre-build validation job runs first to fail fast on common workflow
  errors before any platform-specific build starts.
- macOS code-signing variables are explicitly set to manual / empty
  team / empty profile, eliminating the "no signing identity found"
  failures that were intermittent on the GitHub-hosted runners.
- `xcodebuild` invocation hardened against the runner's default Xcode
  selection — `setup-xcode@v1` pins to `latest-stable`.
- macOS app-bundle path detection uses a glob instead of a fixed name,
  so the archive step survives Xcode's occasional renames of the output
  directory layout.

### iOS

- Add `NSLocalNetworkUsageDescription` to `Info.plist`. iOS now shows a
  one-time "Allow JRiver Remote to find devices on your local network"
  prompt on first launch; tapping **Don't Allow** prevents the app from
  reaching Media Center until re-enabled in **Settings → Privacy &
  Security → Local Network**.

### Documentation

- README rewritten with a two-option layout:
  - **Option 1** — Install prebuilt unsigned releases. Step-by-step
    walkthroughs for macOS Gatekeeper bypass (`xattr -dr
    com.apple.quarantine`) and four iOS sideloading paths (Sideloadly,
    AltStore / SideStore, TrollStore, Xcode), with the trade-offs of
    each.
  - **Option 2** — Build from source with Xcode. Covers prerequisites,
    cloning, replacing the original `DEVELOPMENT_TEAM` and
    `PRODUCT_BUNDLE_IDENTIFIER`, signing on a free Apple ID, the iOS
    7-day / 3-app caveats, and a troubleshooting table.
- New `docs/releases/` folder; this is the second entry, after 2.4.0.

### Under the hood

- Extracted all MCWS-driven playback into a new `McwsPlayer` notifier
  ([mcws_player_provider.dart](../../lib/features/player/providers/mcws_player_provider.dart)).
- Moved the `PlayerStatus` calculation out of `Player` and into
  `LocalPlayer`, so both transports now emit `AsyncValue<PlayerStatus?>`
  symmetrically.
- New `PlayerController` interface
  ([player_controller.dart](../../lib/features/player/providers/player_controller.dart))
  with 14 method signatures; both `LocalPlayer` and `McwsPlayer`
  implement it. The unified `Player` provider went from ~270 lines (with
  per-command `_run({remote, local})` boilerplate) to ~80 lines of
  one-liner forwarders, with the transport selection living in a single
  `_controllerFor(zone)` helper.
- `LocalPlayer` now exposes the same `toggleMute` / `toggleShuffle` /
  `cycleRepeat` shape as the MCWS side, computing the next state from
  its own `state.asData?.value` instead of relying on the parent
  provider to derive it.

### Fixes

- macOS release build: signing now happens after the `.app` bundle is
  copied and renamed, ensuring the verification step sees the same
  binary that gets zipped.
- macOS release archive: app discovery walks
  `Build/Products/Release/*.app` instead of assuming `Runner.app`,
  surviving Flutter's occasional product-name rewrites.

## Compatibility

- **Android**: unchanged — the existing APK / AAB artifacts are
  identical in shape to 2.4.0.
- **iOS / iPadOS**: requires re-install on first upgrade so the new
  Local Network entitlement is registered. After install, accept the
  Local Network prompt on first launch.
- **macOS**: prebuilt `.app` is ad-hoc signed; on first launch you may
  need to run `xattr -dr com.apple.quarantine /Applications/JRiverRemote.app`
  or right-click → **Open** to bypass Gatekeeper.

## Known limitations

- Free Apple-ID sideloads of the iOS IPA expire after 7 days and count
  toward the 3-app per-device limit. A paid Apple Developer Program
  membership lifts both, but the project does not currently distribute
  team-signed builds.
- The macOS `.app` is ad-hoc signed only — not notarized — so first
  launch always trips Gatekeeper on a freshly downloaded copy.

## Migration notes for developers

- `playerProvider` keeps the same public API; consumers of `playPause`,
  `stop`, `next`, etc. don't need code changes.
- Anything that read `localPlayerProvider.future` continues to work, but
  the resolved type is now `PlayerStatus?` instead of `void`. Awaiting
  it without using the result still compiles.
- `LocalPlayer.setMute(bool)`, `setShuffle(ShuffleMode)`,
  `setRepeat(RepeatMode)` are now private to the local player — call
  `toggleMute()`, `toggleShuffle()`, `cycleRepeat()` instead.
- New tagged builds depend on `subosito/flutter-action@v2` and
  `maxim-lobanov/setup-xcode@v1`. If you fork the workflow, update both.
